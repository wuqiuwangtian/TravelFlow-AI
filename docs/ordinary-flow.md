# 普通用户少操作验收：选城承接与对话恢复

2026-10-28，前端升级收口后的第一批主流程走查。沿用已确认的 D3／M1、C1／P1、R1／W1 与三主题，不增加节点或设置。

## 本批发现与修复

### 选过城市却又被推荐一轮

旧 collector 对每条消息都重新调用字段提取模型。已保存城市候选后，用户回复“第二个”，若模型漏掉 destination，程序会再次推荐，用户还得再选一次。用旧提交和漏提取替身已复现此路径，原来的理想模型测试不能发现它。

现在对已保存候选和明确短选择直接承接：序号、中文数字、全角数字，以及“就选成都吧”等城市名表达可进入下一步，保留原预算、日期、人数和偏好，不额外调用字段提取模型。序号越界只说明现有候选，不重排或重新检索，不生成空版本。该承接只在其余必填条件齐全、目的地尚未确定时使用；预算等复合修改仍走完整语义提取，不丢附带条件。询问、否定和多城市比较不强行套成短选择。

模型返回空白、重复城市时先整理可用项；若没有可用候选，按既有 `LLM_OUTPUT_INVALID`／422 返回可重试错误，不输出一份空列表让用户继续选择。原请求重试后沿用已有出行条件，真正选定后才生成计划。后续检索与规划仍需要相应服务，不把“少一次字段提取调用”说成无需模型。

### 历史读取失败看起来像刚开始

旧前端在历史读取失败时清空消息并吞掉错误，用户刷新后容易误以为需要重新讲需求。现在在对话区原位显示等待、失败与重试，保留已显示内容和输入，不在读取未完成或失败时显示新对话引导。

读取请求按分支和消息修订隔离，迟到快照不能覆盖新发送的内容；切换分支保留该分支合法继承的历史，不混入旧分支迟到的内容或路书。历史重试只读对话，不额外读取路书，不触发再次发送或保存。等待期间仍可继续输入、发送，反馈遵守共享样式与手机宽度。

## 已走通的任务

1. 从上海出发、三天、少走路，先请求城市推荐；补预算后直接给候选，不再问需不需要推荐。
2. 刷新后回复短序号；越界时保留候选，选定后形成每日行程。
3. 一条对话记录完成状态和 86.35 元实付，再修改第一天的安排，实付保留。
4. 主动打开回顾、编辑自己的文字、保存并结束旅行；原版本、实际消费和用户原文保留。
5. 从回顾阅读页查看记录并导出，阅读与导出不增加版本。

这条路线使用固定模型与真实本地编排、持久化及导出接口，证明操作承接与数据一致性；不评判真实模型所生成景点的质量或外部服务可用性。回顾仍是可选操作，打开、采用和保存的边界没有被自动化代替。

## 2026-10-29 接续：条件摘要与路书读取恢复

核对 `3e67c3f` 交接基线、干净工作区与实际源码后，支持现有路线：主体功能已经覆盖旅前、旅中和旅后，接下来优先修复普通用户主流程中的上下文断点与失败恢复。不重新选择前端风格、架构或扩充高级节点。

生成前右侧现集中显示出发地、天数、预算及已提取的其他条件、真实缺项、保存阶段和城市候选。摘要来自当前分支 checkpoint 的公开字段，普通与流式回复同步携带；刷新读取不调用模型或产生版本，不解析聊天文字推测状态。日期、人数和预算口径留空时不填默认值，零元预算保留；已要求推荐时不把目的地再列为必须先填的条件。旧客户端与没有摘要的旧请求回执继续兼容，后者重放后由历史接口恢复当前摘要。

路书独立区分没有版本、读取中与读取失败，失败就近提供重试，不再显示成没有计划。后台失败保留同分支已读内容和同版本费用表单草稿，切换分支不显示旧路书；历史选择仍只读，迟到的较新版本不会覆盖后选的旧版本。重试路书不重读对话、不重新生成、不写版本。手机已有计划但读取失败时，恢复区域优先出现在首屏，「今日」可直达恢复位置；读回后继续原 M1 路线布局。

## 2026-10-30 接续：未定目的地的真实服务与重启恢复验收

使用全新临时 SQLite 数据库，通过正式流式对话接口调用当前配置的 DeepSeek 模型（`deepseek-flash`）、DeepSeek 网页检索和高德。没有读取个人旅行、改动服务配置或写入真实订单；密钥、临时数据库和原始响应不入库。

本次真实调用走通：

1. 输入上海出发、两天、两人、园林和博物馆、少走路、目的地和日期未定。只追问预算，没有要求先自行选城市，也没有替用户填日期。
2. 关闭连接并重建应用后，补充「全团预算2000元」，直接推荐扬州、常熟、平湖；出发地、天数、人数、偏好和预算口径保留，推荐阶段不创建行程版本。
3. 再次重建应用后，越界回复「第十个」只说明原有三个候选，不调用模型或检索、不重排候选。
4. 回复「就选第一个吧」后，对研究阶段三路检索注入一次整体不可用故障。返回可重试错误，保留已选扬州和出行条件，不保存半份版本。此故障为受控注入，不是实际 DeepSeek 服务中断。
5. 恢复真实检索并重新打开 SQLite，同一请求直接继续检索和生成，没有重做字段提取或城市推荐。生成两日、11个停留项及14条检索引用，保存一个版本。重建应用后再重放原请求，没有模型／检索调用或额外版本。

结果说明的是一次真实联调，不是推荐城市质量、营业、班次、票价或可预订性的证明。样例只有5个停留项取得明确定位，其余仍有歧义或缺少精确地点；未知费用共4项。页面集中显示待核对地点、未知费用和时间提醒，预算提示仅含已知费用，不能凭当前清单认定整趟旅行节省。住宿尚待明确，检索中的参考车次也不能视为日期未定情况下的已确认安排；没有做真实手机硬件或多日实走验收。

## 2026-10-30 接续：住宿与往返交通的费用覆盖

真实扬州样例中，首站填写了高铁费用却没有对应到达路段，返程只到目的地车站、没有返回出发城市的路段；原先仅提示已有清单的未定价格，无法指出未列入清单的范围。现在费用摘要额外提供只读覆盖提醒：逐晚住宿、已知跨城旅行的去程／返程，以及首站上未归属路段的交通信息。已有未知金额继续由原清单提示；不补造价格、不自动增加支出、不把单程旅行改成往返。

覆盖检查只使用结构化城市、路段及预算项目。明确命名的去程、返程或往返自定义交通项可补足对应范围，普通市内打车不会替代大交通；登记住宿方式和零元费用后保留为已知，不强制酒店消费。它是核对提示，不证明每项费用都正确或已经预订；复杂地点称呼、未明确命名的整趟预算仍可能需要用户说明。

提醒同步到集中核对区、费用面板及Markdown／HTML导出，历史版本读取和导出不写回路书、账目或新版本。分类标题区分预估未列、待核实、部分已知和明确零元，避免空住宿清单显示成已确认免费。

生成提示补充了「出发车站→到达车站→酒店」的交通归属示例，要求住宿逐晚说明、往返费用进入对应结构化路段。一次真实模型／DeepSeek检索／高德调用生成了包含去程、返程和过夜安排的两日样例，同时暴露出到站活动费与铁路票价重复的问题。新生成数据仅对同额、同口径、非人工的铁路／航班到站重复费用去重；人工金额、不同费用和原始实付不推测、不改写。用该真实模型输出在最终规则下回放，两笔270元铁路费用分别只保留在交通段。未将规则倒用于旧版本或宣称所有模型定价均已核实。

## 2026-10-30 接续：对话补充住宿、往返交通与实付归属

真实扬州样例复现了普通修改只采用消息中首个行程日的问题：同时要求第1天去程和第2天返程，接口回复成功，但第二天仍保留原来的缺失返程。现按明确指定的行程日集合分别采用与校验，未指定的天数逐项保留；「第N晚」按第N天的住宿处理。每个指定日仍保护其旅中起点之前的记录、预约及结束点，旅中窗口和两日联动继续沿用各自约束。明确改变旅行总天数时可新增或删减日程，越界日不会被当作全局修改。

模型没有返回某个指定日时拒绝保存，返回可重试错误，不把仅完成部分天数的修改当成成功；普通与流式接口均验证同一请求失败后可恢复，再次重放不多存版本。修改提示同时区分单项住宿预估与整趟预算，要求往返交通分别具备起终点，票价要求未知时不从旧报价补齐。

费用表核对还发现，「第4站午餐」这类旧消费标题没有匹配到「午餐（淮扬菜）」预估，派生预计数将二者重复相加。新记账在站序有效时关联现有活动ID，无法定位的原记录继续保留；旧账本只在同日、同类别、名称唯一匹配时归入已有项目，同名歧义、跨日和显式预算关联不强行合并。原始标题、金额、付款日和关联记录不因只读汇总改写。导出使用所选版本结构化快照的副本重新投影费用表，保持与页面一致，不回写旧路书或账本。

使用临时数据库副本调用真实模型和高德，复用已保存的DeepSeek检索资料：一次补齐两天铁路往返和第一晚全团300元住宿预估，票价保留未知；原86.35元实付、125元人工餐饮预估及完成记录保留，重放原请求不再生成版本。午餐实付归入原预估项后移除了派生视图的额外86.35元累加，不代表旅行节省；未知票价、寄存费用和第2天首站前未定位起点的交通提醒仍保留。该样例不是价格、酒店预订或实际多日出游证明。
