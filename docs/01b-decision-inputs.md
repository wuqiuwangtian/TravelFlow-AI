### ⚠️ 需要你操作的一件事（阶段④前置）

**Docker Desktop 已安装在 Windows 侧**，且存在 `docker-desktop` 发行版，但**当前 Arch 发行版未启用 WSL 集成**，因此在 WSL 内 `docker` 命令不可用：

```
NAME              STATE      VERSION
* Arch            Running    2
  docker-desktop  Stopped    2      ← 存在，但未集成到 Arch
```

**操作路径**：Docker Desktop → Settings → Resources → WSL Integration → 勾选 `Arch` → Apply & Restart。

完成后在 WSL 内 `docker --version` 应可用。**阶段④若选 Docker 部署，这一步是必需的**；现在做或到阶段④再做都可以。

> 附带价值：Docker 修好后，也能顺带解决当前 TUN 模式的容器网络问题。

## 3. D2 / D3 后端与依赖：实测事实

**实测**：按旧 `requirement.txt`（无版本约束）安装，当前得到：

```
langchain 1.4.4 | langchain-core 1.6.9 | langgraph 1.2.14 | langchain-openai 1.7.0
```

而旧代码写于 2025-12，对应的是 `langchain 0.3.x` / `langgraph 0.2.x` 时代 —— **跨了大版本**。

两个实测结论（均在 01 报告 7 节）：

1. **旧代码在 1.x 下仍能 import 并跑通主干**（`collector → researcher → planner` 实测正常），说明**不是硬性不兼容**；
2. 但 `get_graph()` 的可视化输出在 1.x 下已与 0.2.x 不同（Mermaid 只渲染出部分边），**API 行为存在静默差异** —— 这类差异不会报错，只会让调试和可观测性失真。

> 决策所需事实：**锁旧版本（0.3.x/0.2.x）能最大化与现有代码的连续性；上 1.x 则需按新 API 重写编排层。** 两者都可行，取决于 D2 选"最小重构"还是"顺势升级"。

## 5. D5 LLM / 检索：实测事实

- 现有：DeepSeek（OpenAI 兼容接口）+ Tavily
- Tavily `advanced` 检索单次耗时量级：**2~5s**（由 01 报告 7.5 的延迟注入实验推算）
- 当前一次完整生成 = 3 次串行检索 ≈ **6~15s**，且并发能力为 1（实测 2 并发 = 3.01s，完全串行）
- **检索质量已实证**（01 报告 7.7）：产出中的票价、避雷等信息经权威来源交叉验证**大体属实**，Tavily 链路有效；问题出在 query 硬编码年份导致的信息过时，而非检索能力本身

## 7. D7 引用可信链路：事实与可行性

**现状**：Prompt 要求 LLM"保留调研数据中的 URL"，程序**零校验、零回填**。

**实测**：抽样 6 条 URL —— `bendibao` 返回 200（真实）；5 条知乎全部 403（知乎对非浏览器请求统一拦截，**无法据此判定真假**，此验证手段已失效）。

**关键技术事实**：Tavily 的响应本身就是**结构化**的：

```python
response['results'] -> [{'title': ..., 'url': ..., 'content': ...}, ...]
```

即 URL 在检索结果中是独立字段。**程序完全可以直接映射，无需让 LLM 参与引用生成。** 这一点决定了 D7 在技术上没有障碍，纯粹是设计取舍。

## 8. D8 PDF 导出：事实

- 现状：函数名为 `generate_pdf_file`，实际只写 `.md`；依赖 `fpdf2` 已安装但从未 import
- **中文字体是硬约束**：fpdf2 生成中文 PDF 必须嵌入 CJK `.ttf` 字体文件
- 该字体资产不存在于仓库；`backend/static/`（曾被删除）中也没有字体，只有 3 份 `.md` 产物

> 因此 D8 若选"保留 PDF"，需要额外解决字体文件的分发与打包问题（体积 +2~10 MB）；若选 Markdown，则零成本。
